# Device enrolment v1

[`spec.md`](spec.md): the sealed enrolment blob (225 bytes), its fingerprint and the USB
console protocol. [`vectors/vectors.json`](vectors/vectors.json) pins the blob byte for byte;
the firmware's C and the server's Go both reproduce it.
[`vectors/negative.json`](vectors/negative.json) holds the negative cases below.

- **Status:** stable. Exercised on real hardware.
- **Support window:** for as long as any firmware that enrols this way is supported.
- No network credential travels over this channel: the dongle has none.

## Negative cases

[`vectors/negative.json`](vectors/negative.json) (generated by `mkvectors` in the server repository,
each derived from the first positive vector with one thing wrong). The verdict is the first refusal of
the acceptance path: decode the text, parse (length, magic, version, ids, signature), compare the
fingerprint the operator typed, unseal.

- **`bad_signature`**: a flipped signature bit; a signature by another key; any header, ciphertext or tag
  edit without re-signing.
- **`unseal`**: the same edits re-signed (the AAD must still refuse them); a swapped public key re-signed
  by that key; a low-order ephemeral key; a blob sealed to another server key.
- **`malformed`**: bad magic, unsupported version, all-zero device id, key version 0, 224 / 226 / 0 bytes,
  an all-zero sealed root, and non-canonical text (extra padding, inner space, truncated, URL alphabet).
- **Fingerprint**: mismatch, missing, wrong length, not hex.
- **Sequences (server state)**: an identical replay is idempotent and succeeds; a replay after the key
  version was crypto-shredded or the device revoked is refused; a different root at the same key version
  and a different signing key for an enrolled device id are refused.

The dongle only seals blobs and never opens one, so the firmware and emulator have nothing to refuse
here; the server's Go is the reference opener. The vectors have been checked against an independent
opener written from `spec.md` alone.
