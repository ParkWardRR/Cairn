# sync/v1 vectors

Two files, for two jobs.

| File | What it pins |
|---|---|
| [`vectors.json`](vectors.json) | The signing string, body hash and header layout for four request shapes, and the enrolment proof. Signatures are randomised (made once, must **verify**). |
| [`exchanges.json`](exchanges.json) | 83 whole request/response exchanges against one server, in order: the positive paths and the negatives. Signatures are deterministic (RFC 6979), so the file is reproducible and the `Authorization` header is a byte-exact expectation. |

`exchanges.json` is generated by the server's code, not written by hand:

    CAIRN_CONTRACTS=<this contracts directory> \
      go test ./internal/syncapi -run SyncExchange -update-vectors      # in cairn-vehicle-server

Regenerating produces no diff. The server's CI replays the recorded requests against the
server and requires the recorded responses back.

**Status: draft.** The server produces and checks these; that is not independent validation.
`sync/v1` stays `draft` until the iOS app passes them (see [`../README.md`](../README.md)).

## How a client uses `exchanges.json`

The steps are one timeline against one server and must be taken **in order**: replay, expiry,
revocation and cursors depend on what came before. Each step is self-contained (full request,
full response), so a mock server can serve the recorded responses.

- **Build the request.** From a step's `request` and `signing` (`ts`, `nonce`, `client_id`)
  rebuild `signing.signing_string` and require it equal. Sign with the key in `fixture.clients`.
  CryptoKit signatures are randomised, so *verify* `signing.signature_der_base64` with the
  client's public key rather than comparing bytes. `signing.matches_request: false` marks a
  step where the request actually sent differs from what was signed (tampered target or body):
  a string rebuilt from the request as sent will **not** equal `signing_string`.
- **Parse the response.** `response.status`, `response.error_code`, `response.headers` and
  `response.body_json` (compare as JSON) are what the client must handle. CBOR bodies (the
  receipt) are `body_hex`; verify the receipt with `fixture.receipt_signing_public_key_ed25519_hex`.
- **The clock.** `server_clock_unix` is the server's clock for the step. Use the step's
  `signing.ts`, not your own clock.
- **Opaque values.** The bearer token, cursors and epoch are whatever the server drew. They
  appear verbatim only because later steps reuse them; a client must not parse them.

## Cases

| Category | Steps (`name`) |
|---|---|
| Health, enrolment | `health`, `enrol_admin`, `enrol_alpha`, `enrol_bravo_after_bad_proof`, `enrol_charlie`; negatives `enrol_bad_proof` (invitation not consumed), `enrol_code_already_used` |
| Bearer tokens | `token_mint_alpha`, `token_mint_charlie`, `token_valid_at_exactly_one_hour`, `token_mint_after_expiry`; negatives `token_on_signed_only_route`, `token_expired` |
| Signed push | `push_accepted`, `push_duplicate`, `push_with_bearer_token`, `push_mutable_accepted`; negatives `push_rejected_scope`, `push_rejected_unknown_vehicle`, `push_rejected_archived_vehicle`, `push_rejected_hash_mismatch`, `push_rejected_operation_id_conflict`, `push_rejected_client_mismatch`, `push_mutable_conflict`, `push_malformed_body`, `push_no_operations` |
| Signed pull and ack | `pull_first_page`, `pull_second_page`, `pull_second_page_again` (a cursor is repeatable), `pull_last_page`, `pull_with_bearer_token`, `ack_accepted`; negatives `pull_bad_cursor`, `pull_cursor_from_another_epoch` (410), `pull_bad_limit`, `ack_bad_cursor`, `ack_unknown_field` |
| Vehicle scoping | `pull_scoped_to_other_vehicle`, `pull_all_vehicles`; snapshot negatives `snapshot_scoped_client_must_name_a_vehicle`, `snapshot_other_vehicle`, `snapshot_unknown_vehicle` (same 403 as a real car), `snapshot_malformed_vehicle`; `admin_route_as_user` |
| Bundle relay | `relay_offer`, `relay_chunk_0`, `relay_chunk_1`, `relay_chunk_2_bearer`, `relay_commit`, `relay_commit_again`, `relay_receipt`, `relay_reoffer_after_commit`; negatives `relay_offer_out_of_scope`, `relay_chunk_after_refused_offer`, `relay_offer_without_signature_header`, `relay_offer_bad_manifest_signature`, `relay_receipt_before_commit`, `relay_commit_with_chunks_missing`, `relay_chunk_wrong_bytes`, `relay_chunk_out_of_scope`, `relay_commit_out_of_scope`, `relay_receipt_out_of_scope` |
| Authentication negatives | `auth_baseline` then, each one thing wrong: `auth_replay_same_header`, `auth_bad_signature`, `auth_signed_with_another_key`, `auth_target_changed_after_signing`, `auth_body_changed_after_signing`, `auth_unknown_client`, `auth_skew_121s_behind`, `auth_skew_121s_ahead`, `auth_nonce_too_short`, `auth_missing_header`, `auth_unknown_scheme`, `auth_header_missing_signature`, `auth_unknown_bearer_token`; the window's edges `auth_skew_120s_behind_is_accepted`, `auth_skew_120s_ahead_is_accepted` |
| Revocation | `revoke_charlie_works_before`, `revoke_charlie_token_works_before`, `revoke_charlie`; negatives `revoked_client_signed_request`, `revoked_client_bearer_token` |

Not covered: the 200 Parquet body of `GET /v1/snapshot` (the analytical store's output, not the
sync protocol's; only its scope decisions are) and the administration listings.

## These are public test keys

Everything in `fixture` is committed to a public repository and protects nothing.
